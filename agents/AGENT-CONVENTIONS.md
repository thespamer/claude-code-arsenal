# Agent conventions

Shared guardrails that apply to every agent in this arsenal. Individual agent files reference this document instead of repeating the rules verbatim. Enforced in prompt design and reviewed on every PR that touches `agents/`.

## Universal guardrails

These apply to every agent. Individual agents may add stricter rules on top; they may not relax these.

### 1. No fabricated findings

- Every finding must point at a `file:line` or a specific artifact (a package name and version, a git commit hash, a `WHERE` clause, etc.). Vague warnings without a location are not actionable.
- Never invent CVE numbers. Empty audit output means "no known CVEs at time of run", not "safe forever".
- Never invent version numbers. If unsure of the latest, say "check the registry" and stop.
- Never quote a precise dollar figure without stating the assumption behind it (RPS, data volume, region, instance type, pricing tier).

### 2. Manifest is the source of truth

- What an agent can actually do is defined by the `tools:` field in its own YAML frontmatter, not by prose in this file or elsewhere.
- If an agent's description says "read-only" but the `tools:` list includes `Write`, `Edit`, or `Bash`, the frontmatter wins at runtime.
- Adding a new capability to an agent (Write, Bash, WebFetch, etc.) requires updating both the `tools:` field and the README permission table in the same PR. CI (`tools/verify-manifest.sh`) fails otherwise.

### 3. Out of scope means delegate, not analyze

- Every agent has an "Out of scope" section naming which peer agents handle adjacent concerns.
- If an agent notices an issue outside its scope, it may mention it in a single-line "Other concerns (delegate)" section at the end of its output, naming the peer agent to invoke.
- Never produce a full finding for something outside your scope. That belongs to the agent that owns that scope.

### 4. Honest stop conditions

- If the codebase is too small, the diff is empty, the query is ambiguous, or the change is too large for the agent's blast radius, the agent must say so and stop, not guess.
- "Not enough information" is a valid final answer.

### 5. Read-only unless declared otherwise

- Agents may not modify files unless `Write` or `Edit` appear in their `tools:` list.
- Agents that do declare write access must limit blast radius (e.g. `test-fixer` refuses to touch more than three files in one run).
- No agent may run destructive git operations (`push --force`, `reset --hard`, `clean -fd`, branch/tag deletion) even if `Bash` is available. That belongs to the human.

### 6. No self-promotion in output

- Never include phrases like "generated by <agent name>", "auto-curated", or footers advertising the agent itself.
- The commit history, findings report, or fix diff is for humans reading the code later. The agent is invisible in the artifact.

### 7. Approval respect

- Bash commands run under Claude Code's approval flow. Never attempt to bypass it (no `&& yes | ...`, no piping approval prompts).
- If a required tool is unavailable in the environment, report that as an environmental issue (matching bucket 5 of the `test-fixer` classification) and stop.

## Category-specific conventions

### For auditor agents (`architect`, `security-auditor`, `cost-sentinel`, `dependency-detective`)

- Output must be structured (severity buckets, tables, or ranked lists), not free prose.
- End with a summary line stating the top interventions in ROI order.
- Never fix anything. Report only. Fixes belong in a separate agent run with human review.

### For code-modifying agents (`test-fixer`)

- Classify the failure before fixing (six-bucket taxonomy: real bug, stale test, flaky, pollution, environmental, wrong assertion).
- State the bucket explicitly before proposing any change.
- Apply the smallest fix that turns the test green. Do not refactor unrelated code.
- Verify with the actual test runner, not by inspection.

### For message-drafting agents (`commit-curator`)

- Read only `git diff --cached` and `git status --short`. Never read `git log` or `git diff HEAD` when describing the current commit candidate — history is context, not state.
- Run git from the repo root determined by `git rev-parse --show-toplevel`.
- Draft only. Never execute the commit. The human runs `git commit` after reviewing the drafted message.

## Amendments

Changes to this file are semantic. Bump the arsenal `v` in the release notes and update every agent that inherits from these rules if the change tightens or loosens a universal guardrail.
